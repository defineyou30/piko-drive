판정: 현재 v3는 컨셉 문서와 실제 시연물이 서로 다른 상태다. 심사위원은 새 아이디어가 아니라 기존 v2 펫에 기능 목록을 붙인 기획서로 볼 가능성이 높다.

## 1) 떨어질 가장 큰 이유 Top 5

### 1. 핵심 차별 기능이 실제 구현과 불일치한다

문서는 뒷좌석 착석·벨트·뒷문 신호가 핵심이라고 하지만, 현재 `PleosVehicleGateway`는 조수석 착석만 처리한다.

- 모델에도 `passengerPresent`만 존재
- 뒷좌석 착석 필드 없음
- 벨트 신호 처리 없음
- 뒷문 신호 처리 없음
- 남김 방지 상태머신 없음
- 보호자 알림 구현 없음

즉 시연 시 심사위원이 보는 것은 “아이 안전 루틴 앱”이 아니라 기존 v2의 운전 반응형 펫이다. 차량특화성 점수를 가장 크게 잃는 지점이다.

### 2. “아이의 안전 습관”이라는 문제와 해결 효과가 입증되지 않는다

벨트 체결과 준비물 챙기기를 캐릭터가 말한다고 해서 아이가 실제로 습관을 형성한다는 근거가 없다.

특히 다음이 빠져 있다.

- 아이가 몇 살인지
- 벨트를 안 맸을 때 어떤 행동 변화가 일어나는지
- 부모 잔소리 대비 효과가 있는지
- 오탐·미탐 시 아이가 어떻게 반응하는지
- 반복 사용 후에도 리텐션이 유지되는지

“스티커를 모으면 습관이 생긴다”는 가설을 검증하지 않은 채 효과처럼 서술한다. 사업성보다 먼저 사용자 가치가 불확실하다.

### 3. 남김 방지 기능이 안전 기능으로 오해될 수 있다

“아이 방치 방지”, “강한 경고”, “음성 반복”은 심사위원에게 사실상 안전장치로 들린다. 그러나 센서 오류·착석 인식 실패·아이 외 물건 감지·시동 상태 예외를 처리하지 못하면 위험하다.

문서의 “OEM 기능의 보완”이라는 표현만으로는 부족하다. 시연 중 경고가 울리지 않거나 반대로 오경보가 발생하면, 캐릭터 서비스가 아니라 안전 기능의 신뢰성 실패로 평가된다.

### 4. 기능이 너무 많아 3주 안에 어느 것도 완성도가 높아지기 어렵다

현재 추가하려는 범위가 다음처럼 넓다.

- 뒷좌석 신호
- 벨트 신호
- 뒷문 신호
- 루틴 상태머신
- 성장 시스템
- 캐릭터 리디자인
- 아이 이름
- 요일별 준비물
- 보호자 알림
- 보호자 화면
- 푸시 구조
- 실차 매핑 재검증

특히 벨트 API는 에뮬레이터 주입 UI조차 없고, 보호자 알림은 목업이다. 결과적으로 발표 때 “동작하는 핵심”보다 “향후 만들 기능”을 설명하게 될 가능성이 높다.

### 5. 사업성이 안전 데이터 수익화로 너무 빨리 확장된다

가족 구독, 캐릭터 스킨, 통학차량 B2B, 보험 제휴까지 제시하지만 실제 구매 주체와 비용 구조가 불명확하다.

- 부모가 차량용 펫에 구독료를 낼 이유가 약함
- 제조사가 기본 탑재할 때의 비용·운영 주체가 없음
- 통학차량은 개인 차량과 운영·책임 구조가 다름
- 보험 제휴는 민감정보와 책임 문제가 먼저 발생함
- “Pleos 탑재 차량 10만 대”는 가정일 뿐 시장 근거가 아님

사업 확장안을 많이 적을수록 오히려 핵심 사업 가설이 검증되지 않았다는 인상을 준다.

## 2) ‘창밖동화’와 비슷하다고 느낄 지점과 회피책

심사위원이 비슷하다고 느낄 지점은 다음이다.

- 차량 안에서 아이를 대상으로 한다
- 차량 신호나 위치를 활용한다
- 음성으로 콘텐츠를 제공한다
- 캐릭터가 아이와 상호작용한다
- 반복 탑승을 게임·보상 구조로 만든다
- 부모에게 아이의 차량 이용 상황을 전달한다

특히 “요일별 준비물 확인”, “아이 이름 부르기”, “스티커 성장”, “캐릭터의 말”은 동화·퀴즈 대신 다른 형태의 아동용 콘텐츠로 보일 수 있다.

회피하려면 발표 구조부터 바꿔야 한다.

- 위치 기반 콘텐츠, 동화, 퀴즈, LLM을 완전히 제외
- “아이를 즐겁게 하는 앱”이 아니라 “차량 신호로만 작동하는 출발·하차 루틴 엔진”으로 정의
- 캐릭터는 주인공이 아니라 상태 피드백 UI로 축소
- 핵심 데모는 `착석 → 벨트 → 주행 → P → 하차 확인` 한 흐름만 보여주기
- “재미”보다 센서 이벤트와 상태 전이의 정확성을 전면에 배치
- 창밖동화가 위치를 콘텐츠로 바꾼다면, 이 앱은 차량 상태를 행동 확인으로 바꾼다는 차이를 명시

즉 동화의 대체재가 아니라 차량용 안전 루틴 인터페이스라는 카테고리를 만들어야 한다.

## 3) 안전·법적·프라이버시 리스크

### 아이 데이터

아이 이름, 탑승 시간, 하차 시간, 요일별 학원 정보는 개인 식별 가능성이 있는 생활 패턴 데이터다.

- 실제 이름 대신 로컬 별칭 사용
- 목적지·학원명 저장 금지
- 원시 탑승 이력 최소 보관
- 보호자별 접근권한과 철회 기능 필요
- 서버 전송 여부를 명시
- 아이 음성 녹음·STT를 사용하지 않는 구조가 안전함

“데이터는 차 밖으로 나가지 않는다”는 문구와 “다른 보호자에게 자동 알림”은 서로 충돌한다. 푸시 알림을 하려면 최소한 차량 밖 통신과 보호자 식별이 필요하다.

### 남김 방지 경고의 책임

앱이 경고를 했다는 이유로 보호자가 확인 의무를 소홀히 할 수 있다. 반대로 경고가 누락되면 제작자에게 책임을 묻는 기대가 생긴다.

따라서 발표와 UI에서 다음을 명확히 해야 한다.

- 안전장치가 아니라 보조 알림
- 아이의 존재·부재를 보증하지 않음
- 센서 미수신·오류 시 “확인 불가” 표시
- OEM 경고를 대체하지 않음
- 경고 발생 여부와 실제 안전 확보를 동일시하지 않음

### 센서 오류

문서 자체가 착석 매핑 반전과 벨트 주입 불가를 인정한다. 이 상태에서 “아이 방치 방지”를 내세우면 가장 위험하다.

- 좌우 좌석 매핑 오류
- 카시트·가방을 아이로 오인
- 아이가 잠깐 내렸다 다시 탄 경우
- 문 개폐 이벤트 누락
- 차량 전원 종료와 앱 프로세스 종료 간 타이밍 문제
- 네트워크·푸시 실패

이 예외 상황을 시연에서 설명하지 않으면 안전성 점수가 오히려 깎인다.

### 법적 표현

통학차량으로 확장하며 도로교통법상 운전자 의무를 언급하는 것은 위험하다. 법률 준수 솔루션처럼 읽힐 수 있지만, 현재 앱은 법적 의무를 충족시키는 검증된 시스템이 아니다. 해당 내용은 3주 발표에서 삭제하는 편이 낫다.

## 4) 3주 안에 가능한 최소 범위

남겨야 할 것은 하나의 완결된 차량 루틴이다.

`뒷좌석 착석 감지 → 벨트 체결 확인 → 주행 중 잠금 → 주차 후 하차 체크 → 완료 피드백`

다만 실제 신호가 확보되지 않으면 “실차 안전 기능”이라고 발표하면 안 된다. 그 경우에는 데모 입력임을 전면 표시해야 한다.

빼야 할 것:

- 보호자 실시간 푸시
- 서버·계정·다중 보호자
- 요일별 준비물
- B2B 통학차량
- 보험 제휴
- LLM·STT·위치 기반 콘텐츠
- 캐릭터 스킨과 복잡한 성장 단계
- 배터리·충전구·조수석 인사
- 운전 습관 분석
- 남김 방지의 안전 보증 표현

구현 우선순위는 다음이 적절하다.

1. 뒷좌석 1개 좌석만 지원  
2. 벨트·문·기어 이벤트를 하나의 상태머신으로 연결  
3. 주행 중 터치·긴 음성 차단  
4. 이벤트 로그로 각 전환을 화면에 표시  
5. 데모 패널에서 센서 입력과 시뮬레이션 입력을 명확히 구분  
6. 마지막에 캐릭터 표정과 짧은 음성만 얹기  

3주 발표에서 보여줄 목표는 “아이를 즐겁게 한다”가 아니라 “차량 신호가 실제 행동 루틴을 자동으로 진행시킨다”여야 한다.
