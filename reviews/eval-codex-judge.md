## 1) 탈락·하위권이 될 가장 큰 이유 5가지

1. **차량 특화성이 ‘차량 데이터로 펫 표정 바꾸기’ 수준에 머문다.**  
   기어·속도·UX 제한을 읽지만, 결과는 캐릭터 표정과 음성뿐이다. 내비게이션, ADAS, 충전, HVAC, 동승자 상태, 주행 맥락과 연결되지 않아 차량용 앱이라기보다 자동차 안에서 실행되는 펫 앱으로 보인다. 기획서도 휴게소 안내·주간 히스토리를 후속 과제로 미뤘다. `submission/기획서.md:33-39`

2. **창의성의 핵심이 픽셀 펫 하나로 제한된다.**  
   “운전자에게 잔소리하지 않고 펫이 놀란다”는 콘셉트는 이해되지만, 급제동을 감정 캐릭터로 치환한 수준이다. 운전 습관 개선 효과를 입증할 실험, 개인화, 가족·동승자·장거리 상황별 차별화가 없다. 성장도 5단계 픽셀 점등으로 단순해 반복 사용이 빨리 소진될 가능성이 높다.

3. **기술 활용성이 SDK 나열에 비해 제품 경험으로 증명되지 않는다.**  
   Pleos Vehicle SDK, AAOS 속도, TTS, UX restriction을 사용하지만, 심사 화면에서 보이는 것은 “기어에 따라 화면을 바꾸고 속도 변화에 반응하는 애니메이션”이다. 기술이 사용자 가치로 변환된 증거가 부족하다. 특히 “발화 30초 간격”, “표정 10초 제한”, “급제동 임계값”은 안전 구현 증거이지 기술적 차별화 자체가 아니다. `README.md:21-27`, `qa/EVIDENCE.md:16-28`

4. **사업성이 가설과 후속 계획에 의존한다.**  
   주간 사용률 60%, 4주 리텐션 40%는 검증 전 가설이다. 제조사 번들, IAP, 보험 연계도 모두 단계별 계획일 뿐 현재 제품 안에 사업적 확장 근거가 없다. 차량에 기본 탑재됐을 때 사용자가 왜 매일 실행해야 하는지, 기존 차량 운전점수·웰니스 기능과 무엇이 다른지 설득력이 약하다. `submission/기획서.md:41-47`

5. **출품작의 범위가 MVP와 데모 사이에 걸쳐 있다.**  
   “완성된 차량 앱”으로 보기에는 주행 중 프로세스 종료 시 트립 데이터가 유실되고, 휴게소 안내·히스토리·모바일 연동이 빠져 있다. 반면 데모 패널과 성장 가속 기능은 시연을 위해 별도로 존재한다. 심사위원 입장에서는 실제 제품보다 심사용 시나리오를 맞춘 프로토타입으로 판단할 가능성이 크다. `qa/EVIDENCE.md:54-63`, `README.md:56-60`

## 2) 디자인·폰트·UI 품질에서 아마추어처럼 보이는 부분

- **화면 대부분이 지나치게 비어 있다.**  
  F0와 F0b에서 좌측 캐릭터와 우측 문구 사이가 넓고, 콘텐츠가 화면 중앙에 떠 있다. 2560×1440 기준 `PikoSpace.xl = 64dp` 패딩, 좌우 `weight` 기반 배치라 실제 차량 디스플레이 비율에 따라 중심축이 쉽게 무너진다. `Screens.kt:75-101`

- **F1 정차 홈의 정보 밀도가 낮고 시선 흐름이 약하다.**  
  캐릭터, 한 줄 상태, 버튼 3개뿐이다. “오늘 3번 함께 탔어요 · 편안했던 시간 24분”은 정적인 문장처럼 보이며, 리포트·성장·최근 변화의 우선순위가 구분되지 않는다. `Screens.kt:118-149`

- **주행 화면의 픽셀 바가 의미를 설명하지 못한다.**  
  F3 하단의 12칸 바는 무엇이 채워지는지, 다음 정차에서 어떤 결과가 생기는지 알 수 없다. 주행 중 텍스트를 제거한 안전 정책은 이해되지만, 시각적 상태 변화만으로는 정보성이 낮다. `Screens.kt:163-181`

- **픽셀 아이콘이 전문적인 차량 HMI 아이콘처럼 보이지 않는다.**  
  Report·Settings 아이콘은 7×7 문자열을 단순 Canvas로 그린 형태이고, 아이콘 의미가 즉시 전달되지 않는다. `Components.kt:30-76`, `Components.kt:78-87`

- **버튼이 웹·게임 UI에 가깝다.**  
  4dp 라운드, 앰버 단색 채움, 텍스트 중심의 큰 버튼이 반복된다. 차량 HMI에서 기대하는 일관된 컨테이너, 명확한 pressed/focused/disabled 상태가 보이지 않는다. 클릭 가능한 `Row`에 상태 변화도 없다. `Components.kt:90-117`

- **폰트 크기는 크지만 계층이 단조롭다.**  
  `display=40sp`, `title=28sp`, `body=22sp`, `label/caption=18sp`로 대부분의 텍스트가 큰 편인데, 굵기·색상·간격만으로 정보를 분리한다. 화면 캡처에서 본문과 보조 문구가 모두 크게 보여 전문적인 정보 설계보다 목업 느낌이 강하다. `Tokens.kt:44-50`, `Theme.kt:19-26`

- **폰트 파일을 포함했지만 실제 차량 최적화 검증이 없다.**  
  Pretendard Regular/Semibold/Bold를 등록했으나 글자 폭, 한글 줄바꿈, 차량 해상도별 baseline, 시스템 확대 설정에 대한 대응이 없다. 특히 F0의 문장과 F6 리포트의 긴 라벨은 해상도나 폰트 스케일이 달라지면 쉽게 깨질 수 있다. `Theme.kt:13-26`

- **설정 화면이 너무 원시적이다.**  
  F8은 설정 항목 2개와 세그먼트 버튼만 있어 실제 차량 앱 설정으로서 피드백, 현재 상태 설명, 적용 시점, 음성 테스트 결과가 부족하다. 화면 캡처 기준으로도 넓은 빈 공간이 대부분이다.

- **F9 데모 패널이 제품 화면과 분리된 내부 도구처럼 보인다.**  
  5회 탭으로 진입하는 숨은 메뉴는 심사 시에는 유용하지만, 제품 완성도를 오히려 떨어뜨린다. “성장 가속 ×360”, “목소리 테스트”, “피코 처음부터 다시”는 실제 사용자 기능과 시연용 기능이 섞여 있다.

- **캐릭터시트와 실제 UI의 캐릭터 표현이 불일치할 위험이 있다.**  
  캐릭터시트는 표정·성장단계를 정리했지만, 실제 `PikoCanvas`는 상태에 따라 눈·몸·실루엣을 즉석 조합한다. 화면 캡처만 봐도 성장 단계별 캐릭터의 형태적 차이가 작고, 감정 변화가 표정 몇 칸으로 제한된다. `PikoCanvas.kt:114-164`

- **접근성·입력 상태가 사실상 없다.**  
  `clickable`만 사용하고 semantics, content description, focus, keyboard/rotary navigation, pressed state, hover state가 없다. 차량용은 터치만으로 평가되지 않으며, 시스템 포커스와 음성·로터리 입력을 고려하지 않은 UI는 감점 요소다. `Components.kt:102-107`, `Screens.kt:131`

## 3) 코드 품질·아키텍처에서 개발자 심사 시 감점할 부분

- **UI와 화면 상태가 한 파일에 과도하게 몰려 있다.**  
  F0, F1, F3, F6, F7, F8, F9, 캐릭터시트가 `Screens.kt`에 집중되어 있다. 화면별 상태·레이아웃·도메인 변환이 분리되지 않아 변경 영향 범위가 크고, 테스트 가능한 UI 모델도 부족하다. `app/src/main/java/com/pikodrive/ui/screens/Screens.kt:1` 이후

- **`LiveScreen`이 내비게이션·상태 변환·비즈니스 규칙을 동시에 담당한다.**  
  화면 키 계산, 첫 실행 플로우, 리포트 표시, 데모 진입, 야간 밝기, 날짜 변환, 리포트 UI 변환이 하나의 Composable 파일에 섞여 있다. UI 재구성·세션 재생성·백스택 처리에서 버그가 생기기 쉬운 구조다. `ui/live/LiveScreen.kt:54-145`, `ui/live/LiveScreen.kt:148-211`

- **숨은 데모 진입이 하드코딩되어 있다.**  
  800ms 안에 단계 라벨을 5번 탭하면 데모 패널이 열린다. 제품 코드에 심사 전용 진입 로직이 남아 있고, 테스트도 이 제스처에 의존한다. `LiveScreen.kt:130-138`

- **UI 상태와 저장 상태가 이중화되어 있다.**  
  `PetState`를 `PetUi`로 변환하면서 성장 단계, 진행률, 문구를 별도로 계산한다. `stage`와 `comfortMinutesTotal`이 서로 다른 기준으로 표시될 수 있으며, 표시용 계산이 화면 파일에 있어 도메인 규칙이 분산된다. `LiveScreen.kt:160-180`

- **시간 표현 변환이 취약하다.**  
  monotonic time을 wall-clock으로 변환해 저장하고 다시 monotonic으로 복원한다. 프로세스 재시작, 시스템 시간 변경, 장시간 절전, 시간대 변경에 취약한 방식이며 리포트 시간의 신뢰성이 떨어진다. `DataStorePetRepository.kt:17-20`, `DataStorePetRepository.kt:61-63`

- **리포트 저장 포맷이 직접 문자열 직렬화다.**  
  `|`와 `,`를 구분자로 사용해 한 줄 문자열로 저장한다. 버전 필드, 스키마 마이그레이션, 손상 데이터 복구가 없고 포맷 변경 시 기존 리포트가 전부 무효화될 수 있다. `DataStorePetRepository.kt:46-55`, `DataStorePetRepository.kt:65-82`

- **차량 게이트웨이의 수명주기와 연결 관리가 세션 수집에 종속된다.**  
  `callbackFlow`가 닫히면 Car 연결을 끊고 Pleos 객체를 해제한다. 구성 변경, 백그라운드 전환, 재시작 시 차량 연결 상태가 복원되는지 구조적으로 명확하지 않다. `PleosVehicleGateway.kt:60-70`, `PleosVehicleGateway.kt:136-145`

- **게이트웨이의 nullable 처리와 기능 판정이 방어적으로 보이지만 계약이 약하다.**  
  `props`가 null이어도 `capabilities`가 계산되고, 기어·속도·UX가 부분적으로만 들어오는 상태를 코어가 처리한다. 그러나 화면과 안전 정책이 “미확인 상태”를 사용자에게 어떻게 보장하는지 명확한 상태 모델이 없다. `PleosVehicleGateway.kt:39-50`, `PleosVehicleGateway.kt:161-169`

- **PetEngine이 단일 스레드 전제를 문서 주석에만 의존한다.**  
  “scope는 단일 스레드여야 한다”고 적혀 있지만 타입이나 실행 구조로 강제하지 않는다. 차량 콜백, Flow 수집, 지연 반응, TTS 중단이 서로 다른 실행 맥락에서 들어오면 상태 경합 위험이 있다. `PetEngine.kt:19-27`, `PetEngine.kt:79-120`

- **음성 스케줄러와 주행 이벤트의 실제 실패 상태가 제품 화면에 연결되지 않는다.**  
  `DROPPED_BUSY`, `DROPPED_BUDGET`, `DROPPED_MODE`를 로그로 남기지만 사용자에게는 음성이 왜 나오지 않았는지, 마지막 반응이 무엇인지 보이지 않는다. 심사자가 “정말 안전 정책이 동작한 것인지” 확인하려면 로그를 봐야 한다. `PetEngine.kt:187-217`

- **테스트가 코어 규칙 중심이고 UI·차량 통합 경계가 약하다.**  
  README의 53개 테스트는 판정·엔진 정책 검증이지 Compose 화면, Android lifecycle, Pleos SDK 실패, 저장소 마이그레이션, 화면 재구성 검증이 아니다. 따라서 핵심 데모가 되는 실제 앱 경로의 회귀 위험이 남아 있다. `README.md:63-68`, `submission/기획서.md:33-38`

- **제품 코드에 목업 모드와 실시간 모드가 함께 남아 있다.**  
  `MainActivity`가 `screen` 인텐트로 목업 화면을 직접 선택한다. 심사용 갤러리로는 편하지만, 운영 코드와 테스트 코드의 경계가 불명확하고 실제 진입 경로와 목업 경로가 같은 화면을 다른 상태로 렌더링한다. `MainActivity.kt:31-34`, `MainActivity.kt:46-57`, `MainActivity.kt:72-87`

## 4) 시연(PT)에서 터질 수 있는 위험

- **시작부터 P단·UX restriction·속도 권한 상태가 맞아야 한다.**  
  권한, Pleos SDK 연결, AAOS 폴백, Virtual Console 포트 포워딩 중 하나만 어긋나도 첫 화면이 주행 안전 화면으로 고정되거나 기대한 기어 전환이 나오지 않을 수 있다.

- **시연용 성장 가속 ×360이 제품 기능으로 오해될 수 있다.**  
  심사위원이 실제 성장 속도와 데모 성장 속도를 구분하지 못하면 제품 설계의 신뢰도가 떨어진다. 반대로 데모 패널을 보여주지 않으면 짧은 PT 시간 안에 성장 장면이 나오지 않을 수 있다.

- **90초 시나리오가 너무 많은 상태 전환에 의존한다.**  
  출발, 칭찬, 급제동, 후진, 정차, 리포트까지 여러 신호가 순서대로 들어와야 한다. 차량 신호 지연, 콘솔 연결 끊김, TTS 포커스, 앱 재시작 중 하나만 발생해도 스토리라인이 깨진다.

- **TTS가 PT의 핵심인데 오디오 포커스와 환경 소음에 취약하다.**  
  기획서상 음성은 주행 중 유일한 소통 채널이다. 음성이 나오지 않으면 화면에는 정보가 거의 없어져 제품 가치가 즉시 약해진다. 오디오 실패는 단위 테스트로 완전히 증명되지 않았다. `qa/EVIDENCE.md:54-63`

- **F3 화면이 너무 비어 있어 관객이 상태 변화를 놓칠 수 있다.**  
  주행 중 텍스트·버튼을 제거한 결과, 멀리서 보는 PT에서는 급제동·편안한 주행·후진의 차이가 작게 보일 가능성이 높다. 안전을 지키면서도 상태 변화의 시각적 대비가 더 필요하다.

- **리포트 수치가 데모마다 달라질 수 있다.**  
  실행 시간, 콘솔 이벤트, 이전 저장 상태에 따라 `+87`, `+88` 같은 수치가 바뀐다. 기획서·영상·캡처의 숫자가 일치하지 않으면 조작된 데모처럼 보인다.

- **첫 실행 플로우가 길다.**  
  F0 → F0b → 출발까지 두 번의 버튼 클릭이 필요하다. PT 시작 직후 첫 화면 설명과 앱 가치 설명에 시간이 소요되고, 심사위원의 질문 시간이 줄어든다.

- **정차 후 자동으로 리포트가 뜨는 정책이 사용자의 의도와 충돌할 수 있다.**  
  주차 직후 화면을 만지거나 설정으로 가려는 순간 리포트가 우선 표시된다. 제품 데모에서는 가능하지만 실제 UX에서는 강제 인터럽트로 느껴질 수 있다. `LiveScreen.kt:81-85`, `LiveScreen.kt:97-99`

## 5) 제출 전 반드시 고칠 Top 7

1. **차량 특화 기능을 하나 추가하라.**  
   예: 60분 연속 주행 감지 후 정차 시 휴식 지점 안내, 충전 잔량 기반 휴식 제안, 또는 내비 목적지 도착 맥락과 리포트 연결. 단순 기어·속도 반응만으로는 부족하다.

2. **F3 주행 화면의 상태 대비를 강화하라.**  
   텍스트를 늘리지 않는 조건에서 급제동·편안한 주행·후진을 픽셀 색상, 표정 실루엣, 화면 밝기, 짧은 모션으로 명확히 구분하고, PT용 캡처에서 3m 거리에서도 식별되게 검증하라.

3. **숨은 데모 패널과 제품 코드를 분리하라.**  
   `LiveScreen.kt:130-138`의 5회 탭 진입을 제품 빌드에서 제거하고, 별도 debug/demo flavor 또는 외부 시연 컨트롤러로 이동하라.

4. **UI 공통 컴포넌트에 상태·접근성·입력 처리를 추가하라.**  
   `PikoButton`에 pressed/focused/disabled/semantics/contentDescription을 구현하고, 모든 화면에서 rotary·키보드 포커스 순서를 검증하라. 현재 `clickable`만으로는 차량 HMI 품질을 충족하지 못한다.

5. **리포트 저장 구조를 버전 있는 직렬화 모델로 교체하라.**  
   문자열 구분자 저장을 없애고 schema version, 벽시계 기준 timestamp, 손상 레코드 복구, migration 테스트를 추가하라. 현재 구현은 시간·포맷 변경에 취약하다.

6. **실제 앱 경로에 대한 통합 테스트를 추가하라.**  
   Pleos SDK 실패, 속도 권한 거부, UX restriction 미확인, 차량 신호 끊김, 프로세스 재시작, TTS 포커스 실패, 정차 자동 리포트 표시를 각각 테스트하고, 단위 테스트 53개와 분리해 보고하라.

7. **사업성 주장을 검증 가능한 제품 지표로 바꿔라.**  
   “주간 사용률 60%, 4주 리텐션 40%” 같은 가설을 전면에 두지 말고, 실제 구현된 리포트·성장·휴식 제안이 어떤 반복 행동을 만드는지 측정 이벤트와 실험 설계를 제출하라. 현재 사업 모델은 구현보다 선언이 앞서 있다.
