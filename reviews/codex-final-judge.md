## 2. 감점 요인 Top 7

### 1) 핵심 안전 기능의 벨트 입력이 실제 차량 신호가 아님

- 근거: `submission/기획서.md:40`, `qa/EVIDENCE.md:4`, `qa/EVIDENCE.md:11`
- 영상 근거: 영상 자막에 “벨트는 시연용 대체 입력”이 반복됨.
- 문제: 벨트 미체결 출발 경고와 주행 중 벨트 풀림이 제품의 핵심인데, 심사 영상에서는 실제 SDK 입력이 아니라 데모 패널 입력이다. 심사위원 입장에서는 가장 중요한 안전 판단 로직의 실차 신뢰도를 확인하기 어렵다.
- 수정 분류: **구현·검증 필요**
- 20일 내 수정안:
  - 실제 Pleos 에뮬레이터 또는 공식 입력 경로에서 벨트 상태를 바꾸는 재현 방법을 확보한다.
  - 불가능하면 제출물 전면에서 “벨트 감지 구현 완료”와 “에뮬레이터 주입 미지원”을 분리해 표기한다.
  - 영상 시작 10초 안에 실제 신호와 대체 입력을 비교하는 검증 화면을 넣는다.
  - 최소한 벨트 신호의 타임스탬프·원시값·앱 판단값을 함께 보여주는 증거 화면을 추가한다.

### 2) 실차 검증 전인데 안전 보조 기능의 표현이 다소 강함

- 근거: `submission/기획서.md:9`, `submission/기획서.md:18-20`, `submission/기획서.md:32`
- 문제: “탑승부터 하차까지 함께 챙긴다”, “차가 체크한다”는 문구는 실제 차량에서도 안정적으로 감지되는 것처럼 읽힌다. 그러나 `qa/EVIDENCE.md:87`에는 실차 착석 방향과 운전자 하차 후 동작 시간이 미검증으로 남아 있다.
- 수정 분류: **기획서 문장 수정 + 일부 구현 검증 필요**
- 수정안:
  - “차량 신호가 정상 수신되는 범위에서 탑승·하차 상황을 보조한다”로 한정한다.
  - “안전 확인” 대신 “안전 보조 알림”을 일관되게 사용한다.
  - 실차에서 검증되지 않은 조건은 영상과 화면에 “에뮬레이터 검증”으로 표시한다.

### 3) 남김 알림의 오탐·미탐 조건이 충분히 설명되지 않음

- 근거: `submission/기획서.md:19`, `submission/기획서.md:32`, `qa/EVIDENCE.md:35-37`
- 코드 근거: `core/src/main/kotlin/com/pikodrive/core/ride/RideEngine.kt:301-327`
- 문제:
  - 착석 신호가 남아 있으면 알림을 발생시키지만, 센서가 잘못되거나 착석 신호가 늦게 해제될 때의 사용자 대응이 약하다.
  - “운전석이 비었거나 정차 중 문을 잠갔는데”라는 조건은 실제 운전자 하차 감지와 차량 잠금 타이밍에 의존한다.
  - 보호자 알림은 첫 번째 남김 경보만 전송한다는 구현 제약이 기획서에 드러나지 않는다.
- 수정 분류: **구현·검증 필요**
- 수정안:
  - “감지 실패 시 직접 확인”을 전체 화면과 보호자 메시지 모두에 표시한다.
  - 알림에 감지 시각, 감지 좌석, 센서 상태를 포함한다.
  - 운전자 하차 후 5초, 10초, 30초 등 시간 조건별 오탐 테스트를 추가한다.
  - 남김 알림을 차량 기본 경고와 혼동하지 않도록 “보조 알림”을 가장 큰 제목으로 노출한다.

### 4) 보호자 알림은 제품 기능처럼 보이지만 실제로는 로컬 웹훅 시연임

- 근거: `submission/기획서.md:22`, `submission/기획서.md:49`, `README.md:81`, `qa/EVIDENCE.md:85`
- 코드 근거: `app/src/main/java/com/pikodrive/guardian/GuardianNotifier.kt:24`, `:90`, `tools/guardian_server.py:6`
- 문제: 기획서의 “다른 보호자에게 보냅니다”는 실제 푸시 알림처럼 읽힌다. 실제 검증은 `127.0.0.1` 로컬 서버이며, 푸시·계정 연동은 후속 과제다.
- 수정 분류: **기획서 문장 수정**
- 수정안:
  - “보호자가 지정한 웹훅으로 이벤트를 전송하는 프로토타입”이라고 명시한다.
  - “푸시·계정 연동은 출시 전 구현 대상”을 사업 계획에 별도 표기한다.
  - 영상의 “6건 전송” 문구는 “로컬 웹훅 6건 전송”으로 고친다.
- 추가 위험: 기본 URL이 `http://127.0.0.1:8099/event`이고 일반 웹훅 인증·HTTPS·재전송 보장이 보이지 않는다. 실제 서비스 기능으로 평가하면 기술 점수가 깎일 수 있다.

### 5) 음성 입력 성능이 실제 사용성을 뒷받침하지 못함

- 근거: `qa/EVIDENCE.md:64-69`
- 영상 근거: “못 알아들은 칸은 칩으로” 장면이 빠르게 지나가며, 실제 인식 실패율은 화면에 명확히 드러나지 않음.
- 문제: “짧게 말하면 알아들은 칸이 채워진다”는 장점보다, 일정 제목 “태권도”가 6회 중 2회만 정확했다는 사실이 더 중요하다. 실제 사람 목소리·차량 소음 환경은 미검증이다.
- 수정 분류: **기획서 문장 수정 + 구현 검증 필요**
- 수정안:
  - “음성으로 자동 입력”이 아니라 “음성으로 초안을 만들고 칩으로 확정”으로 정의한다.
  - 인식 confidence 또는 “확인 필요” 상태를 UI에 명확히 표시한다.
  - 실제 차량 마이크와 어린이·성인 음성으로 최소 30회 테스트해 결과를 제시한다.
  - 음성 실패 시 사용자가 다시 말하거나 칩 입력으로 이어지는 경로를 영상에서 보여준다.

### 6) 후석 화면과 조명 기능의 실차 적용 범위가 불명확함

- 근거: `submission/기획서.md:21-22`, `qa/EVIDENCE.md:16`, `qa/EVIDENCE.md:20`, `qa/EVIDENCE.md:60-62`
- 문제:
  - 뒷좌석 화면은 실제 후석 디스플레이가 아니라 보조 디스플레이에서 검증됐다.
  - 에뮬레이터에서 보조 디스플레이를 붙이면 시스템 앱이 종료되는 불안정성이 기록돼 있다.
  - 앰비언트 조명은 5좌석 묶음 영역을 제어하므로 “아이만 조용히”가 아니라 차량 전체 조명이 낮아질 수 있다.
- 수정 분류: **기획서 문장 수정 + 구현 검증 필요**
- 수정안:
  - “뒷좌석 화면이 있는 차”를 “탑승자 구역 디스플레이가 지원되는 차”로 제한한다.
  - 쉿 모드는 “실내 앰비언트 전체 밝기를 낮춤”이라고 표현한다.
  - 후석 화면 미지원 차종에서 음성만으로도 핵심 루틴이 완결되는 장면을 영상에 넣는다.
  - 차종·디스플레이·조명 API 지원 매트릭스를 제출한다.

### 7) 사업성 수치가 가정에 머물고 비용 구조가 없다

- 근거: `submission/기획서.md:45-49`
- 문제:
  - “Pleos 탑재 차량 10만 대”, “자녀가 있는 가구 30%”, “설치 10%”, “4주 리텐션 50%”가 모두 가정이다.
  - 사용자가 누구인지, 현대차그룹이 어떤 방식으로 수익을 얻는지, 기본 탑재인지 유료 옵션인지, 보호자 서버 운영비가 얼마인지가 없다.
  - 차량 신호 지원 여부에 따라 차종별 기능이 달라질 가능성이 큰데 “전반에 적용”으로 넓게 말한다.
- 수정 분류: **기획서 보강 필요**
- 수정안:
  - 시장 규모 대신 1차 파일럿 목표를 제시한다. 예: “Pleos 지원 패밀리 차종 2종, 30가구, 4주”.
  - KPI를 설치율보다 `벨트 미체결 출발 시도`, `남김 알림 확인 완료 시간`, `준비물 알림 사용률`, `오탐률`로 제시한다.
  - 기본 탑재·무료 옵션·구독형 중 하나를 선택하고 보호자 서버 비용과 개인정보 처리 책임을 설명한다.
  - 지원 API별로 “필수 기능 / 제한 기능 / 미지원 기능”을 차종 매트릭스로 만든다.

## 4. 영상에서 헷갈리거나 지루할 지점

### 헷갈리는 지점

1. **실제 기능과 시뮬레이션 입력의 구분이 늦게 인식될 수 있음**  
   벨트 장면에서 대체 입력이라는 자막은 나오지만, 심사위원은 처음부터 실제 차량 신호인지 데모 조작인지 구분하기 어렵다.

2. **영상이 음성 시연이 아니라 자막 시연으로 보임**  
   `tools/make_video_v3.py:64-67`에서 오디오 입력을 `anullsrc`로 넣는다. 코드 주석도 앱 음성이 녹화되지 않아 자막으로 넣는다고 명시한다. 즉, “차량 음성 비서”가 핵심인데 실제 발화는 들리지 않는다.

3. **앱 화면, Pleos 원 화면, PIP의 관계가 복잡함**  
   좌측 앱 확대 화면과 우측 설명 패널, 우측 상단 PIP가 동시에 등장한다. 심사위원은 어느 화면이 실제 사용자 화면이고 어느 화면이 개발·검증 화면인지 순간적으로 판단해야 한다.

4. **“아이를 두고 내리면”이 실제 위험 방지인지 사후 알림인지 모호함**  
   영상 첫 장면에서 강한 훅을 사용하지만, 감지 시점과 알림 시점을 설명하지 않으면 “차량 잠금 후 즉시?” “운전자가 일정 거리 이동한 뒤?”가 불명확하다.

5. **“뒷좌석 화면”이 실제 차량의 후석 화면처럼 보일 수 있음**  
   실제 근거는 보조 디스플레이이고, 실차 후석 구역은 미검증이다. 자막에서 보조 디스플레이라는 사실을 더 크게 표시해야 한다.

### 지루해질 지점

1. 설정·음성 입력·칩 보정 장면이 연속으로 길다. 심사위원에게 가장 중요한 차량 루틴 장면이 뒤로 밀린다.
2. “에뮬레이터 실측”, “루틴 9장면”, “단위 테스트 134개” 카드가 영상 후반에 몰려 있어 제품 가치가 이미 소진된 뒤 숫자가 나온다.
3. 주행 중 피코 얼굴만 남는 장면은 안전 설계상 의미는 있지만 화면 변화가 적다. 4배속 처리되어도 설명이 부족하면 단순 정지 화면으로 보인다.
4. 보호자 화면은 웹훅 수신 결과인지 실제 모바일 푸시인지 구분하기 어렵다.

## 5. 개인정보·안전 표현에서 문제될 지점

### 개인정보

1. **별칭도 개인정보가 될 수 있음**  
   별칭·좌석·시각이 결합되면 특정 가족과 이동 패턴을 추정할 수 있다. “별칭만이므로 개인정보가 아니다”처럼 읽히지 않게 해야 한다.

2. **보호자 알림의 외부 전송 경계가 약함**  
   `GuardianNotifier.kt`는 보호자가 입력한 URL로 전송한다. URL 검증, HTTPS 강제, 인증, 인증서 검증, 재전송 정책이 제출물에서 보이지 않는다.

3. **로컬 저장소 암호화 근거가 없음**  
   `DataStore` 사용은 저장 위치를 설명할 뿐 암호화를 보장하지 않는다. “차 안에만 있다”와 “안전하게 보호된다”를 혼동하면 안 된다.

4. **음성 데이터 처리 표현을 더 정확히 해야 함**  
   기기 내 인식이라고 해도 STT SDK의 실제 처리 경계와 로그·임시 파일 존재 여부를 확인해야 한다. 현재 QA에는 `voice_inject.pcm`을 앱 파일 영역에 넣는 개발용 경로가 있다. 제출 문서에는 이것이 실제 사용자 음성 저장 경로가 아니라 QA 전용임을 분리해서 써야 한다.

5. **보호자 동의와 철회가 부족함**  
   어린이 관련 데이터와 보호자 알림은 보호자 동의, 수신자 변경, 알림 철회, 데이터 삭제 기능을 설명해야 한다.

### 안전

1. **차량 기본 경고와의 관계를 더 강하게 표시해야 함**  
   현재 “차량 기본 경고를 대신하지 않는다”는 문구는 있으나, 영상과 주요 화면에서는 잘 보이지 않는다. 남김 알림 화면에서 항상 표시하는 편이 안전하다.

2. **센서 미수신을 정상 상태와 혼동할 위험**  
   `qa/EVIDENCE.md:36`에 원칙은 잘 적혀 있지만, 심사 화면에서는 실제 “확인 불가” 상태가 충분히 드러나지 않는다. `정상`, `위험`, `확인 불가`를 색상만이 아니라 텍스트로 구분해야 한다.

3. **차도 쪽 문 방향의 일반화**  
   코드상 기본값은 왼쪽 뒷좌석을 차도 쪽으로 간주한다. `RideEngine.kt:88`, `RideLines.kt:36`. 차량이 정차한 방향, 도로 형태, 주차장 상황에 따라 달라질 수 있으므로 “차도 쪽”을 자동 확정하면 안 된다. “현재 설정된 차도 쪽 문”으로 표현하고 사용자가 방향을 설정하도록 해야 한다.

4. **앰비언트 조명이 아이만이 아니라 실내 전체에 적용될 수 있음**  
   `AmbientDimmer.kt`의 영역은 여러 좌석이 묶인 전체 영역이다. “아이의 수면을 위해 조명을 낮춘다”가 운전자 시야나 다른 승객의 환경까지 바꾸는 기능처럼 보이지 않도록 제한 조건이 필요하다.

5. **운전 중 음성의 우선순위는 좋지만 과도한 반복 가능성 있음**  
   남김 알림은 10초마다 반복된다. 실제 주행 중 동일 음성이 반복되면 운전자 주의를 분산시킬 수 있다. 반복 횟수, 음량, 운전자 확인 방식, 긴급 알림과 일반 알림의 차등이 필요하다.

## 최종 판단

이 제출물은 단순 아이디어가 아니라 차량 신호, 주행 상태, 음성 정책, 일정·메모를 하나의 루틴으로 묶은 점이 강하다. 특히 `qa/EVIDENCE.md`와 코어 테스트가 있어 개발 신뢰도도 높은 편이다.

다만 현재 감점의 핵심은 다음 세 가지다.

1. **벨트 핵심 경로가 시뮬레이션 입력**
2. **실차·후석 디스플레이·실제 음성 검증 부족**
3. **로컬 웹훅과 가정 기반 사업 수치를 실제 서비스처럼 읽히게 하는 표현**

20일 동안에는 새 기능을 많이 추가하기보다, 핵심 장면의 실차 검증과 제한 조건 공개, 보호자 알림의 보안 경계, 영상의 증거 전달력을 보강하는 것이 점수 상승 효과가 가장 크다.
