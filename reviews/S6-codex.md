## 총평

현재 제출물은 기능 구현과 QA 증거는 상당히 갖춰졌지만, 심사자가 보는 제출 문서 기준으로는 “구현된 MVP”와 “사업·확장 계획”이 섞여 있습니다. 특히 README 실행 경로와 기획서의 링크·산출물 표기가 미완성이라, 실제 점수보다 낮게 평가될 위험이 큽니다.

## 1. 심사 기준별 약점과 수정 문장

### 차량특화성

약점:

- 차량 데이터와 연결된 기능은 명확하지만, “왜 차량에서만 가능한가”가 기어·속도·TTS API 나열에 머뭅니다.
- 휴게소 안내, 모바일 연동, 보험 연계는 아직 미구현인데 확장 기능처럼 읽힙니다.
- `P/R/D` 동작은 잘 설명됐지만 N단과 UX 제한 상태의 사용자 경험이 기획서에 없습니다.

수정 문장:

> 피코는 속도·감속도·기어·차량 UX 제한을 동시에 읽어, 주행 중에는 화면을 자동으로 축소하고 음성만 허용한다. 이 때문에 일반 모바일 펫 앱으로는 구현할 수 없는 ‘차량 상태에 따라 표현 방식이 바뀌는 동승자’ 경험을 제공한다.

> 현재 구현 범위는 P/D/R, 속도, UX 제한, TTS이며, N단 및 휴게소 안내는 후속 개발 항목이다.

### 창의성

약점:

- “운전 습관을 펫의 감정으로 번역한다”는 핵심은 좋지만, 심사자가 한 문장으로 기억할 차별점이 약합니다.
- 아이오닉 파라메트릭 픽셀과 비전 문구를 언급하면서도 독자 IP라는 설명이 뒤에 있어 브랜드 차용으로 오해될 수 있습니다.
- 급제동을 “놀란 펫”으로 표현하는 것이 운전자에게 죄책감이나 주의 분산을 유발하지 않는다는 근거가 부족합니다.

수정 문장:

> 기존 운전 점수 앱이 운전자를 평가한다면, 피코는 같은 차량 데이터를 동승자의 표정·성장·짧은 음성으로 변환한다. 목표는 점수 개선이 아니라 ‘함께 타는 존재를 배려하는 행동’을 반복하게 만드는 것이다.

> 픽셀 형태는 현대차그룹 디자인 언어에서 영감을 얻었지만, 캐릭터·UI·성장 규칙은 본 출품작의 독자 설계이며 공식 제휴·승인과 무관하다.

> 급제동 반응은 2.5초 지연 후 한 문장만 출력하고, 운전자를 비난하지 않으며, 후진 진입 시 즉시 무음으로 전환해 주의 분산을 제한한다.

### 기술 활용성

약점:

- SDK/API 이름은 충분하지만 각 API가 없을 때 어떤 사용자 경험이 사라지는지가 표로 더 명확해야 합니다.
- “발화 중 후진 → 360ms”는 일부는 S0 측정, 일부는 S3 합산값입니다. 현재 문서의 “실측” 표현이 측정 범위를 과장할 수 있습니다.
- 주행 중 표정 변화 제한은 엔진과 렌더러에 구현돼 있지만, 실제 화면 프레임 기반 검증 근거는 약합니다.
- release APK와 데모 로그의 연결은 `verdict.log`로 보강됐지만, README는 여전히 심사자가 APK를 바로 찾기 어렵습니다.

수정 문장:

> 속도·기어·UX 제한은 각각 독립 API로 수집하며, 기어는 Pleos Vehicle SDK 실패 시 AAOS `GEAR_SELECTION`으로 폴백한다. 단, 속도 또는 UX 제한이 확인되지 않으면 안전을 위해 대화형 정차 모드로 추정하지 않고 보수적으로 무음·주행 정책을 유지한다.

> 후진 무음 시간은 콘솔→앱 전달 지연 S0 측정값과 앱 내부 stop 처리 S3 측정값을 합산한 보수적 상한이며, 단일 하드웨어 지연 측정값이 아니다.

### 사업성

약점:

- 타깃은 “Pleos 탑재 차량 오너 30~40대”로 좁지만, 왜 이들이 설치하고 계속 쓰는지 정량 근거가 없습니다.
- MAU 공식은 제시됐지만 차량 대수, 설치 퍼널, 실제 목표 사용자 수가 없습니다.
- `WAU/설치 60%`, `4주 리텐션 40%`는 근거 없는 목표치로 보입니다.
- 보험사 UBI, IAP, 라이선스가 동시에 등장해 초기 사업 모델이 분산됩니다.
- 연속 출근 기록·주간 히스토리는 현재 구현되지 않았습니다.

수정 문장:

> 초기 타깃은 Pleos 탑재 차량을 매일 20분 이상 운전하는 30~40대 출퇴근 사용자다. 이들은 별도 알림 없이 매일 차량에 탑승하므로, 출퇴근 1회를 1세션으로 정의해 설치 후 주간 사용률과 4주 리텐션을 측정한다.

> 출시 초기에는 유료 꾸미기 아이템보다 차량 제조사 번들 앱으로 유입과 반복 사용성을 검증한다. 4주간 사용 데이터가 확보된 뒤 캐릭터 꾸미기 IAP를 검토하고, 보험사 연계는 운전 습관 원자료가 아니라 사용자 동의 기반의 집계 지표만 제공하는 별도 단계로 둔다.

> 현재 구현된 리텐션 장치는 성장·도착 리포트이며, 연속 출근 기록과 주간 히스토리는 후속 버전 항목이다.

## 2. 문서·영상·증거·실제 기능 불일치

### 높은 위험

1. 기획서의 참고자료가 미완성 상태입니다.

- `GitHub 저장소: (링크 기재 예정)`
- `시연 영상: (파일명/링크 기재 예정)`
- 숏폼 링크도 `(게시 후 기재)`로 남아 있습니다.

제출본에서 그대로 보이면 완성도 감점 요소입니다.

2. README의 APK 경로가 실제 저장소와 다릅니다.

README는 다음을 안내합니다.

```bash
adb install apk/*_release.apk
```

하지만 현재 `apk/` 디렉터리는 없고 APK는 `dist/PikoDrive_release.apk`에 있습니다. 심사자가 README만 따라 하면 첫 설치 단계에서 막힙니다.

3. 기획서 5번의 “완성되어 있으며”는 과도합니다.

실제로 미지원 또는 미구현으로 기록된 항목이 있습니다.

- 휴게소 안내
- 모바일 컴패니언
- 주간 성장 히스토리
- 주행 중 프로세스 종료 전 트립 복구
- 오디오 포커스 거부의 에뮬레이터 실측

“앱 전체 완성”이 아니라 “핵심 MVP 완성”으로 낮춰야 안전합니다.

수정 문장:

> 현재 Pleos Connect 에뮬레이터에서 핵심 루프(P/D/R·속도 반응·TTS·성장·도착 리포트)가 동작하는 MVP를 완성했으며, 휴게소 안내·모바일 연동·주간 히스토리는 후속 개발 항목이다.

4. 영상 자막의 “표정 변화는 10초에 한 번까지”는 영상에서 직접 검증되는 문구가 아닙니다.

영상은 117초짜리 합성본이고, 44~68초 구간에 해당 수치를 자막으로 표시하지만 프레임별 검증 결과는 별도 증거에 있습니다. “영상에서 확인 가능”처럼 보이지 않게 바꾸는 편이 정확합니다.

수정 자막:

> 주행 화면은 피코와 픽셀 바만 표시합니다. 표정·발화 제한은 코어 테스트와 QA 로그로 검증했습니다.

5. 성장 단계 표현이 혼재합니다.

기획서는 5단계 `점등→눈뜸→얼굴→몸→완성`을 말하지만, release 데모 증거는 `SPARK→BODY`까지만 도달합니다. 이는 기능 미완성이 아니라 데모 시나리오의 범위일 수 있으므로 명시해야 합니다.

수정 문장:

> 성장 시스템은 5단계로 구현되어 있으며, 제출 영상에서는 90초 시연을 위해 SPARK에서 BODY까지의 변화만 압축해 보여준다.

## 3. README만 보고 실행할 때 막히는 지점

- `apk/` 경로가 실제 `dist/`와 불일치합니다.
- `adb install` 전에 에뮬레이터 연결 확인, `adb devices`, 패키지 제거 여부가 없습니다.
- `pm grant`가 권한에 따라 실패할 수 있는데, 실패 시 계속 진행 가능한지 설명이 부족합니다.
- Pleos SDK 다운로드가 외부 Maven 저장소에 의존합니다. 네트워크가 차단되면 소스 빌드가 불가능합니다.
- ARM64 Pleos 에뮬레이터와 일반 Android 환경의 차이가 큽니다.
- Virtual Console의 실제 실행 위치와 인증·포트 상태 확인 방법이 없습니다.
- `tools/s4_demo90.sh`가 현재 실행 중인 앱 상태, 녹화 권한, 출력 디렉터리 조건을 요구하는데 사전 조건이 README에 없습니다.
- 숨은 데모 패널의 5회 탭은 일반 심사자에게 발견 가능하지 않습니다. 제출 영상용 기능인지, 일반 사용자 기능인지 구분해야 합니다.
- README에는 제출 영상 파일 링크가 없습니다.
- `apk/` 폴더가 없으므로 “release APK가 저장소에 포함되어 있다”는 설명도 현재 상태와 맞지 않습니다.

권장 최소 실행 섹션:

```bash
adb devices
adb uninstall com.pikodrive || true
adb install dist/PikoDrive_release.apk
adb shell pm grant --user current com.pikodrive android.car.permission.CAR_SPEED || true

adb forward tcp:18088 tcp:8088
python3 tools/vconsole.py scenario demo90
```

그리고 첫 줄에 다음을 명시해야 합니다.

> 검증된 실행 환경은 Pleos Connect Emulator v2.1.0입니다. 일반 Android 기기에서는 SIM 모드로 동작하며 Pleos 차량 API 실측을 재현하지 않습니다.

## 4. 개인정보·실명 노출 위험

현재 확인된 직접적인 개인정보 노출은 크지 않습니다.

- 영상과 키비주얼에는 운전자 얼굴·번호판·차량 식별번호가 보이지 않습니다.
- 로그에도 실명·전화번호·이메일은 확인되지 않습니다.
- APK 서명 DN의 `CN=Piko Drive, O=Piko, C=KR`는 개인 실명은 아니지만 팀 식별자로 사용될 수 있습니다.
- 제출 양식 DOCX의 참가신청서와 서명란은 반드시 최종 배포본에서 별도 확인해야 합니다.
- `submission/template/contest-application-consent.docx`와 접수 양식에 작성자 이름·연락처·서명이 남아 있다면 저장소 공개본에서 제거해야 합니다.
- 차량 주행 데이터는 개인정보가 아니더라도 운전 습관 프로파일이 될 수 있으므로, 사업성 문구의 UBI 연계는 “사용자 명시 동의·목적 제한·원자료 미공유”를 명시해야 합니다.
- TTS는 로컬 출력으로 보이지만, 마이크 입력·녹음·외부 전송 여부는 README나 개인정보 처리 설명에 없습니다. “음성 입력을 받지 않고 녹음하지 않는다”를 명시하는 편이 안전합니다.

## 5. 제출 전 꼭 고칠 Top 5

1. `README.md`의 APK 경로와 실제 제출물 경로를 일치시키고, `dist/PikoDrive_release.apk`의 SHA-256과 설치 명령을 README에 직접 적기.

2. `submission/기획서.md`의 GitHub 링크, 영상 링크, 숏폼 링크의 placeholder를 실제 링크 또는 “미제공”이 아닌 제출 가능한 파일명으로 교체하기.

3. “완성” 표현을 핵심 MVP 기준으로 정정하고, 미구현 기능인 휴게소 안내·모바일 연동·주간 히스토리·프로세스 종료 후 트립 복구를 명확히 후속 항목으로 분리하기.

4. 기술 수치의 검증 수준을 통일하기. 특히 `360ms`, `표정 10초 제한`, `급제동 6패턴 정확`을 실차 측정인지, 에뮬레이터 실측인지, 코어 테스트인지 각각 표기하기.

5. 사업성 문단을 초기 사업 모델 하나로 좁히고 근거를 보강하기. 초기에는 “제조사 번들 앱으로 설치율·주간 사용률 검증”, 이후 IAP와 보험 연계 순서로 정리하며 MAU 계산에 실제 가정값을 넣기.

현재 상태 그대로 제출하면 기능 자체보다 문서 완성도와 재현성에서 감점될 가능성이 큽니다. 특히 `apk/` 경로 불일치와 placeholder 링크는 즉시 수정해야 하는 제출 차단 항목입니다.
