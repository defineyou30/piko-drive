# S-1 프레임 리뷰 — Codex gpt-5.6-luna (low), 2026-10-24

## 1) 캐릭터 컨셉·네이밍·상표/IP

- 핵심 컨셉은 이해되지만, 현재는 **현대차 비전과 아이오닉 파라메트릭 픽셀을 너무 직접적으로 차용**한다. “헤드램프 같은 픽셀”, “파라메트릭 픽셀”, “Progress” 성장 규칙이 합쳐져 독자 캐릭터보다 현대차 디자인 자산의 변형처럼 보일 위험이 있다. (`FRAMEWORK.md:12-20`)
- `PLAN.md`는 출품 캐릭터를 **“몽이”**라고 하고, `FRAMEWORK.md`는 앱과 캐릭터를 **“피코”**라고 한다. 이름 혼선은 제출물·영상·APK 불일치로 직결된다. (`FRAMEWORK.md:26-31`, `PLAN.md:21`)
- “몽치의 픽셀아트 아바타와 같은 세계관”은 기존 IP의 2차적 이용·귀속·수상 후 권리 문제를 발생시킨다. 스핀오프라는 명칭만으로 리스크가 줄지 않는다. 설명회 확인 전에는 독립 IP로 가정하면 안 된다.
- `Piko`, `Humi`, `Progi`, `몽이`, `몽치 드라이브` 모두 상표·앱명·도메인·음성 호출어 중복 검색이 없다. “STT 인식률 양호 예상”도 검증 근거가 없다. (`FRAMEWORK.md:22-32`)
- 앱명에 `Pleos`, `IONIQ`, `Hyundai`, `H`를 넣지 않은 점과 모티프 차용 제한은 유지해야 한다. 다만 기획서의 설명 문장에서도 공식 연계·승인처럼 읽히지 않게 “영감”과 “공식 제휴 아님”을 분리해야 한다.

## 2) 비주얼 언어·AI 슬롭·차량 HMI

- 코드 생성 픽셀 매트릭스는 일관성 측면에서 적절하지만, **앰버 단색 + 다크 캐빈 + 픽셀 캐릭터 + step easing**만으로는 차량 브랜드풍 그래픽을 흉내 낸 일반적인 생성형 콘셉트처럼 보일 수 있다. 캐릭터만의 고유한 규칙, 실루엣, 표정 문법이 더 필요하다.
- “AI 이미지 생성 후 수동 정리”는 최종 결과만 정제한다는 기준이 불명확하다. 학습 데이터 유사성, 생성 기록, 라이선스, 상표·디자인 침해 검토 절차가 `ASSETS_LICENSE.md`에 포함돼야 한다. (`FRAMEWORK.md:66-78`)
- PT 키비주얼과 숏폼 썸네일을 AI 생성으로 만들 경우, 앱 UI와 완전히 다른 품질·조명·캐릭터 형태가 될 가능성이 높다. 앱 캐릭터의 픽셀 규칙과 동일한 제약을 문서 이미지에도 적용해야 한다.
- “터치 타깃 76dp”만으로 차량 HMI 적합성을 판단할 수 없다. 주행 중 시선 분산, 화면 밝기, 명암 대비, 야간 눈부심, 애니메이션 빈도, 최소 표시 시간, 시스템 UX 제한과의 충돌 기준이 빠져 있다. (`FRAMEWORK.md:51-56`)
- `F3`의 “표정만”은 안전 측면에서 유리하지만, 중앙 앰비언트 캐릭터가 운전자 시선을 끌 수 있다. 픽셀 스캐터·깜빡임·성장 애니메이션에도 빈도와 지속시간 제한이 필요하다.
- “급제동 = 픽셀 스캐터”는 시각적으로 급제동 사건을 강조해 운전자 불안을 키울 수 있다. 주행 중에는 표정 변화도 최소화하고, 상세 연출은 정차 후 리포트로 미루는 편이 안전하다.

## 3) UX 플로우 누락·모순

- `FRAMEWORK.md`는 F0~F9, `PLAN.md` Must는 F0~F4·F6·F8·F9만 구현한다. F5·F7이 Should라는 사실은 맞지만, 화면 목록과 제출물 기능 목록을 명시적으로 분리하지 않아 심사자가 전체 구현 범위로 오해할 수 있다.
- `PLAN.md`는 주행 중 “음성(TTS/STT)으로만 말을 거는 동승자”라고 쓰지만, Must에는 TTS만 있고 STT는 Should다. 제출 버전의 실제 상호작용은 **TTS 단방향인지, STT가 포함되는지** 하나로 고정해야 한다. (`PLAN.md:10-13`, `66-78`)
- F5의 “TTS + 내비 휴게소 안내”는 안전상 가장 위험한 기능이다. 휴게소 탐색, 경로 변경, 확인 음성 등에서 운전자에게 추가 판단을 요구할 수 있다. PT 이후 기능으로 미루거나, 기존 내비가 제공하는 휴식 알림을 단순 전달하는 수준으로 제한해야 한다.
- `F4 이벤트 반응`과 `PLAN.md`의 급제동 반응은 모순된다. F4는 이벤트 즉시 반응처럼 보이고, 안전 원칙은 2~3초 지연이다. 이벤트 발생→대기→오디오 포커스 확인→발화 실패/폐기 상태를 플로우에 넣어야 한다.
- 앱 재시작 후 “주행 중이면 즉시 F3”는 위험하다. 복구 직후 화면이 노출되기 전에 기어·UX Restriction·앱 권한·오디오 포커스를 재확인해야 한다. (`FRAMEWORK.md:125-129`)
- 기어가 `R`일 때도 F3을 동일 적용한다. 후진 중에는 화면·TTS 모두 더 엄격하게 제한하거나 무반응 정책이 필요하다. (`FRAMEWORK.md:117`)
- 권한 거부 시 “설정 유도”가 정차 시만이라는 조건은 있으나, 설정 진입 전 현재 기어가 P인지 재확인하는 단계가 없다.
- 로컬 음성 처리·녹음 미저장은 적혀 있지만, 마이크 권한, 음성 데이터 전송 여부, TTS/STT SDK의 외부 처리 여부가 확인되지 않았다. 개인정보 문구만으로 해결되지 않는다. (`FRAMEWORK.md:131`)

## 4) Stage Gate 일정 현실성

- 가장 큰 일정 모순은 제출일이다. `FRAMEWORK.md`는 11/14, `PLAN.md`는 접수 마감 11/15라고 한다. 실제 공모전 공고의 공식 마감 시각·시간대를 즉시 하나로 확정해야 한다. (`FRAMEWORK.md:4`, `PLAN.md:4`)
- `PLAN.md`의 P2 MVP는 10/29~11/11이고, `FRAMEWORK.md`는 S2·S3·S4를 10/29~11/10에 순차 완료하도록 잡았다. Pleos SDK 승인·시스템 이미지 설치가 아직 막힌 상태에서 차량 연동, TTS, UX Restriction, 수동 QA까지 12일은 1인 개발 기준 매우 공격적이다. (`FRAMEWORK.md:198-205`)
- S1이 3일 안에 픽셀 렌더러, 5단계 성장, 표정 6종, F0~F9 와이어, 이름 확정을 모두 통과시키도록 되어 있다. 이름·IP 검토가 미완료인 상태에서 구현이 먼저 진행될 위험이 있다.
- S5 안정화와 S6 제출물 제작이 겹친다. 기능 동결 직전까지 엣지 플로우·로그·지표를 만들고, 동시에 DOCX·영상·GitHub·숏폼까지 마무리하는 구조라 버퍼가 사실상 없다. (`FRAMEWORK.md:160-161`)
- PT 고도화에서 Should 2개를 11/16~11/28에 추가하는 계획은 가능하지만, 11/29~12/02에 리허설 3회와 백업 영상 제작까지 하려면 **11/24를 실질적인 기능 마감일**로 앞당겨야 한다.
- Stage Gate 기준이 “리뷰 통과”, “플로우 끊김 0”처럼 추상적이다. 각 게이트마다 필수 증거 파일, 실패 시 범위 축소 규칙, 시간 제한을 지정해야 한다.
- “Codex 리뷰”가 검증 주체로 과도하게 설정돼 있다. 차량 안전·SDK 권한·IP 문제는 모델 리뷰만으로 승인할 수 없고, 실제 에뮬레이터 로그와 공모전 공식 답변이 우선이다.

## 5) 즉시 고칠 것 Top 5

1. **이름과 IP 전략을 하나로 확정**
   - `피코`와 `몽이` 중 하나만 선택.
   - 몽치와의 관계를 제거한 독립 캐릭터로 갈지, 사용 권리를 확인한 스핀오프로 갈지 결정.
   - 상표·앱명·음성 호출어 검색과 공모전 IP 답변을 S1 Gate 필수 조건으로 추가.

2. **제출일과 버전 기준을 하나로 통일**
   - 11/14 vs 11/15, PT 12/3 vs 12/3~4를 공식 공고 기준으로 정리.
   - `v0.1-submit` 실제 제출 버전, 영상 버전, README 기능 목록을 하나의 체크섬 또는 버전표로 묶기.

3. **주행 중 반응 정책을 축소·명문화**
   - 주행 중에는 표정 변화와 TTS 모두 최소 빈도.
   - 급제동 스캐터 삭제 또는 정차 후 재생.
   - R단, UX 제한, 오디오 포커스 실패, 앱 재시작 직후는 무반응 정책 추가.
   - STT는 제출 버전에서 제외하고 PT 이후 후보로 분리.

4. **F0~F9 상태 머신을 안전 조건까지 다시 그리기**
   - `P/D/R`, UX Restriction, 권한, 오디오 포커스, 앱 복구를 전이 조건에 포함.
   - F4 지연 발화, F5 내비 개입, F6 도착 판정의 예외 흐름을 명시.
   - “화면만 숨김”이 아니라 주행 중 터치·음성·애니메이션·발화가 각각 어떻게 제한되는지 정의.

5. **게이트를 증거 중심으로 재설계**
   - S0: 실제 SDK/API별 성공·실패 로그 없으면 차량 연동 개발 중단.
   - S3: D/P/R, UX Restriction, 오디오 포커스, TTS 실패 케이스 영상 확보 전 통과 금지.
   - S4: 실제 90초 데모를 3회 연속 재현해야 통과.
   - S5: 11/10을 기능 동결, 11/11~제출은 버그·제출물만 처리하도록 버퍼 확보.
